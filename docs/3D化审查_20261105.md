## 0. 结论摘要

1. **3D 不是从零开始**：`3d/preview` 已能把 2.5D 地图升维成可走场景（10 舱室 / 11 走廊 / 110 墙段 / 59 掩体），WASD + 鼠标 + 手电 + 碰撞全部跑通，实测位移 4.198/4.2 m/s。代码只有 **594 行 GDScript**。
2. **更大的发现**：`tools/blender-ship.py`（**1391 行**）本来就是一套**程序化船体模型** —— 它建了房间、墙体、掩体、家具、电闸柜、监控墙、服务器柜、管线、灯带，然后俯视烘成 `base-lit.png`。也就是说，**船的三维几何早就存在**，只是从来没导出成 glTF。这是 3D 化最大的加速器。
3. **贴图可以直接用**：25 张 1024² 可平铺材质本来就按世界坐标生成，3D 里 triplanar / UV 平铺即可，不需要重画。
4. **真正的成本不在渲染，在模拟**：`js/game.js` 10,287 行里，绘制/DOM 相关约 **972 行（9.5%）**，其余 **9,245 行是规则、AI、会议、证据链**。3D 客户端能不能"重写"，取决于这 9 千行怎么处理 —— 这是唯一需要你拍板的架构分叉。
5. **两条已经发生的偏移**：`3d/preview/data/map.json` 已过期（任务时长还是旧值），`ASSETS.md` 记录的源哈希也对不上；`map.json` 还缺架构文档要求的 `schema_version`。

## 4. 数据契约现状

`3d/preview/data/map.json` 由 `3d/tools/export-map.cjs`（39 行）从 `js/data/map.js` 导出，这是唯一的跨项目入口（ADR-0004）。

| 项 | 值 |
|---|---|
| 结构 | `scale` / `bounds` / `rooms`(10) / `corridors`(11) / `cover`(59) / `points`(26) / `pipes`(6) / `facility`(6) / `walls`(110) / `decor`(32) |
| 房间字段 | `id / name / cls / light / cut / rect / doors / poly / area / label` |

**审查发现（两处已经发生了的偏移）**：

1. **`map.json` 过期**：`引擎组同步` 在 `map.js` 里 `dur: 7`，在 `map.json` 里还是 `dur: 12`（任务时长那批没重新导出）。ADR-0004 的"代价"条款早就写了"改地图后必须重新导出"，但它没有强制手段。
2. **哈希对不上**：`ASSETS.md` 记的源文件哈希是 `eb9d7991…`，当前 `js/data/map.js` 是 `9d220adc…`（因为时长改过）；`map.json` 的哈希 `b28667a1…` 与记录一致，也就是说**记录的是旧快照**。
3. **缺 `schema_version`**：`3d/ARCHITECTURE.md §3` 硬规则第 6 条要求"`map.json` 带 `schema_version`"，实际没有。

## 5. 三条技术路线（模拟层归属，这是唯一的分叉）

`js/game.js` 里 9,245 行是规则与 AI。3D 客户端要跑起来，必须决定这些代码去哪。

### 路线 A · 用 GDScript 重写模拟

- 做法：把 `sanity.js`(849) / `t2/ai.js`(574) / `t2/decision.js`(206) / `data/lines.js`(1992) / `map.js` 逐块移植；事件 schema 不变。
- 优点：单一运行时，发布干净；性能可控；没有进程间通信。
- 代价：**728 条门禁、1000 局蒙特卡洛、复盘工具全部要重做或重写**；两套实现并存期间，行为漂移无法自动发现。
- 适用：3D 确定要成为**唯一**发行客户端。

### 路线 B · JS 保持权威模拟，Godot 只做表现

- 做法：Node 进程跑现有 `game.js`（`SIM_RUN` 已经能跳过渲染），通过本地 socket 把状态/事件推给 Godot；Godot 只发 intent（移动、交互、投票）。
- 优点：AI、门禁、复盘、蒙特卡洛**全部原样保留**；3D 端可以从零开始做表现，不会把 AI 改坏。
- 代价：发布要带一个 Node 运行时（或打包成单文件）；两进程时序要定协议；`file://` 红线虽不适用，但"双击即玩"会变成"先起服务"。
- 适用：先把 3D 做成**能玩的垂直切片**，同时不欠 AI 的债。

### 路线 C · 先做 view-only 切片，暂不接模拟

- 做法：3D 里只放"玩家 + 场景 + 任务交互"，AI 用几条硬编码巡逻；验证手感、可读性、任务镜头。
- 优点：最快看到东西；不碰任何架构决策。
- 代价：不能验证"3D 下的社交推理可读性"（会议、证据、尸体），而那才是这游戏的核心。
- 适用：**第一阶段**。

**建议**：`C → B →（若 3D 转正）A`。
先用 C 把"镜头放大做任务"这条交互坐实（这是你点名要的形态），再用 B 把真实 AI 接进来验证可读性；只有当 3D 确定取代 2.5D 时，才值得付 A 的代价。反过来先做 A，会在还没验证玩法的情况下重写 9 千行。

## 6. 你提的交互形态怎么落地

> "3D 版直接实时场景把图贴上去；做任务的时候直接把镜头放大，然后直接开始操作这个图。"

这条在 Godot 里有两种实现，建议选第二种：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **世界内平面** | 任务点做一个 `MeshInstance3D` 平面，贴 `panel-*.png`；相机推到正前方；射线打在这个平面上做交互 | 真 3D，遮挡/景深自然 | 拖拽、滑块、文字都要在 3D 里自己写；文字用 `Label3D` 会糊 |
| **相机推近 + Control 层**（推荐） | 相机推到面板前（3D 场景仍是背景），前景用 `Control` 面板，底图是任务贴图，控件用 Godot 原生 Button/ProgressBar | 小游戏布局几乎可以照搬现有 DOM 结构；文字清晰；和"遮罩盖住大半屏"的注意力语义天然一致 | 遮罩是 2D 层，和 3D 贴图是"视觉贴合"而不是"物理贴合" |

**注意力语义可以顺势接上**：相机推近 + Control 遮罩 = `attention='ui'`，玩家看不见有人靠近；把 FOV 收窄还能模拟"余光被挡"。这正好接上 A 批已经落地的三态。

**小游戏移植量**：`js/t2/minigame.js` 708 行 / 10 种玩法。改成 Control 节点是**纯搬运**（布局逻辑不变），但 10 种都要重画一遍，估计 900~1100 行 GDScript。这是 3D 侧最大的一块 UI 工作。
