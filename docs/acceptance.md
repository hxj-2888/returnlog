## 1. 目的与适用

T3 回答「事后看到什么」。本节把这件事写成可核对的规则，覆盖：

- 谁来当真源、谁只能当读数（§3）；
- 台账怎么写、读数怎么留痕（§4）；
- 一个时点只能有一个现行基线（§5）；
- 改了 T2 真源之后，导出快照怎么才算同步（§6）；
- 用什么自动体检挡住复发（§7）；
- 已经存在的历史问题如何登记而不擅自改写（§8）。

**适用起点：2026-11-04**（根 `ARCHITECTURE.md` 三层架构定稿日）。此前的历史批次只标注、不删除、不追认读数（§4.4）。

**不适用范围**：本规范不判断某个数值「该是多少」、某次胜率「是否达标」。数值定义属 T1/T2，平衡裁定属用户；T3 只保证记录可追溯。

## 3. 真源 / 读数分离

### 3.1 判定口诀

> **「改一个行为要动 `js/`，就是真源；只是把跑出来的数字记下来，就是读数。」**

| | 真源（T1/T2） | 读数（T3） |
|---|---|---|
| 回答 | 规则是什么 | 这批跑出来是什么 |
| 修改后果 | 行为改变 | 行为不变 |
| 允许份数 | 每个定义**一份** | 每批可有多条，历史不删 |
| 例子 | `SKSanity.MISID.chance = 0.2` | 「1000 局 74.8% / 25.2%，门禁 849/0」 |
| 能否作为「基线唯一真源」 | ✅ 只有它可以自称真源 | ❌ 永远不可以 |

### 3.2 禁止句式（体检 C1 会拦截）

- ❌ 「数值基线唯一真源是 `tools/mc-report.md`」／「权威口径：数值基线 = `tools/mc-report.md`」
- ❌ 把 `_mc-*.md`、`CHANGELOG.md`、`rules.json` 写成「数值真源」「基线真源」
- ❌ 用某批胜率反推并修改 T2 数值表（属批内回写，见 `ARCHITECTURE.md` §8）
- ✅ 「数值真源见 `js/ai/sanity.js` / `js/data/map.js`；读数台账见 `CHANGELOG.md` 最新批次」
- ✅ 「现行基线见 `CHANGELOG.md` 最新批次的『读数变化』段」

## 4. 台账三段式与读数留痕

### 4.1 固定三段（`CHANGELOG.md:4` 既有规则，此处细化）

每条批次必须依次写全：

1. **本批改动** —— 改了哪些文件 / 哪些参数，旧值 → 新值；纯文档批也要写「未改 `js/` 逻辑与数据」。
2. **读数变化** —— 本批**实跑**结果，见 §4.2。
3. **下一批立项依据（用户裁定后填）** —— 尚未裁定时写「待用户裁定」，不得留空、不得用其它小标题替代。

### 4.2 「读数变化」段的硬要求

- 改了逻辑 / 数据：**必须写当批实跑的 `X 通过 / Y 失败`**，不得沿用旧读数（根 `AGENTS.md` §一.4）。
- 未跑门禁 / 未跑模拟：**必须显式写「未跑门禁」「未跑 sim」或「沿用旧读数（原因）」**，零实测不能沉默。
- 胜率必须带：局数、seed、Wilson 区间（1000 局批次）、以及是否与上一批同批 A/B 可比。
- 数值批的「读数变化」不得只写体积 / 哈希 / PASS 而漏掉门禁数（V3.7 批即为此类）。
- 台账里出现「已同步 / 重导出 / 全空」等**断言**时，必须给出可复核的文件或命令证据（§6）。

### 4.3 跨批比较

跨批**只比同批 A/B 两臂**；不同批次、不同样本量（300 局 vs 1000 局）、不同随机流的读数不得直接相减归因。
「从 A 跳到 B 里只有 X pp 是机制」这类表述，必须附同 seed 的 A/B 实测，否则只写作历史读数、不给归因。

### 4.4 历史条目与补登记

- 2026-11-04 之前的批次按 `CHANGELOG.md:4`「历史条目只标注不删除」豁免三段式，
  但建议在章节体首行加一行「历史条目 · 三段式不适用」以免误读。
- **漏登的历史批次只能「补登记」，不能「追认读数」**：写明「补登记 · 原批次日期 / 时间未载」，
  以代码注释、门禁断言、git 历史为证据；当时没跑的读数就写「原批未留读数，不追认」，
  不得事后编造胜率或门禁数。补登记是否执行由**用户裁定**（见 §8 N1）。

1. **一处声明**：现行基线 / 门禁现值只在 `CHANGELOG.md` 最新批次的「读数变化」段出现一次。

3. **历史读数**：只在对应批次内保留，并在文档里标「历史读数，非现行基线」；**只标注不删除**。

   若来自不同测试套件或不同批次集合，**必须写明口径与交叉引用**，不得混用或互相当作基线。

## 6. 导出快照与跨仓同步

### 6.1 谁派生自谁

```text
js/ai/sanity.js + js/ai/traits.js + js/t2/*.js   ──3d:export:rules──▶ 3d/preview/data/rules.json
js/data/map.js                                   ──3d:export:map ───▶ 3d/preview/data/map.json
js/data/map.js (+ 方案层 v2)                     ──build-map-v2 ─────▶ map_v2.json / layout-v2.json
SKSanity.STAND 等                                ──3d:export:space ───▶ 3d/preview/data/space.json
```

`rules.json#sources` 记录各源文件的 sha1 前 12 位（算法见 `3d/tools/export-rules.cjs:40`），
是「快照是否跟随真源」的唯一可核凭据。

### 6.2 改动 T2 真源后的必做顺序

1. 改 `js/` 真源 → 跑主门禁 `npm test`；
2. 重跑对应 `3d:export:*`（含 `build-map-v2.cjs`，若 `map_v2` / `layout-v2` 属受影响导出）；
3. 跑 `npm run t3:check`，确认「快照哈希」与「2.5D ↔ 3D 导出对账」无新增 WARN；
4. 在台账「本批改动」里写**实际重导的文件名**，不写笼统的「3D 已同步」。

### 6.3 「已同步」断言的证据要求

台账写「已同步 / 重导出 X 同步」时，必须能在该文件中核到新值。
仅重导了 `map.json` 却写「`map_v2.json` 同步」视为**记录错误**（见 §8 M1）。

## 7. 验收层体检（`npm run t3:check`）

| 命令 | 用途 |
|---|---|
| `npm run t3:check` | 常规体检：只读、报告 PASS / WARN / FAIL；WARN 不阻断（存量债） |
| `npm run t3:check:strict` | 严格模式：WARN 也按失败退出，供发版或收口时使用 |
| `node tests/check-t3.cjs` | 直接调用，同上 |

**检查项**（与 `tests/check-t3.cjs` 一一对应）：

| 编号 | 检查 | 判定 |
|---|---|---|
| C1 | 禁止句式：台账 / 报告被称作数值真源 | FAIL |
| C2 | 已废弃的 `mc-report.md` 是否被当作现行文件引用 | WARN / FAIL |
| C3 | 非台账文档是否私自声明「当前基线 / 门禁现值」 | WARN |
| C3b | 历史分册头部是否已加 §5.4 指针（4 份按分册纪律豁免逐行改写） | WARN |
| C4 | `CHANGELOG.md` 三段式完整度（仅 11-04 起） | WARN（聚合） |
| C4b | 11-04 前历史批次豁免计数（只标注不删除） | PASS（信息） |
| C5 | 「读数变化」段是否有当批实跑读数或显式「未跑 / 沿用」 | WARN（聚合） |
| C6 | `rules.json#sources` 哈希与当前 `js/` 是否一致 | WARN / FAIL |
| C7 | `map.js` ↔ `map.json` / `map_v2.json` 运行字段对账（`decor` 属 3D 墙面美术允许差异；`layout-v2` 方案层留档不参与运行时对账） | WARN（聚合） |
| C8 | 版本真源三处一致（`version.js` / `package.json` / `CHANGELOG.md`） | FAIL |
| C9 | 工作区有未提交改动但台账无当日条目 | WARN |
| C10 | 存量债登记（本文件 §8）是否存在 | PASS（信息） |

**分级原则**：能确定违反硬规矩的（C1 / C8）直接 FAIL；历史遗留、需用户裁定或涉及未提交工作区的（C2~C7 / C9）为 WARN。
新增问题一律不得靠「加豁免」消掉；豁免只能登记在 §8 并写明处置人与期限。
本脚本**不接入 `tests/test-v3.cjs`**，不影响主门禁全绿要求（根 `AGENTS.md` §一.4）。

## 9. 改动流程补充（T3 相关）

1. 只改 T3 文档 / 体检脚本：不必跑 `npm test`（未改 `js/` 逻辑与数据），但**必须跑 `npm run t3:check`**

3. 改 T2 真源：按 §6.2 全流程，并同时更新 `CHANGELOG.md` 与导出快照。
4. 发版前：`npm run t3:check:strict` 应无 FAIL；存在 WARN 时须确认 §8 已登记且未新增。
