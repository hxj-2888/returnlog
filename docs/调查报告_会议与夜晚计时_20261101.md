# 调查报告 · 紧急会议不消耗夜晚时间（无限续夜）


> **架构节点**（档 1 · 根 `ARCHITECTURE.md`）：`T3 · 第 3 层验收层 · 增量台账` · `flag: F`；只记录「改了什么 → 读数怎么变」，不作达标线、不回流当前批决策。

> 版本：返航录V3.4 · 2026-11-01 · **本次只调查，未改任何逻辑**
> 结论先说：**根因是一行 `Math.max(8000, …)` 的保底，外加 `finishMeeting` 缺少"时间耗尽 → 天亮"的分支。**
> 结果不是"时间重置成 120 秒"，而是**每次深夜开会都被抬回 8 秒，夜晚永远结束不了**。

---

## 一、复现（实测数据）

探针（临时脚本，已删）：把夜晚压到 10 秒 → 连开三次"报告尸体"会议，每次模拟会议耗时 30 秒。

| 步骤 | 会议开始时夜晚剩余 | 会议结束后夜晚剩余 | 天数 |
|---|---:|---:|---:|
| 起始 | — | **10.0 秒** | 第 1 夜 |
| 第 1 次会议 | 9998 ms | **8.0 秒** | 第 1 夜 |
| 第 2 次会议 | 8000 ms | **8.0 秒** | 第 1 夜 |
| 第 3 次会议 | 8000 ms | **8.0 秒** | 第 1 夜 |

- 第 1 次：`10000 − 30000 = −20000` → 被保底抬到 **8000**。
- 第 2 次：`8000 − 30000 = −22000` → 又被抬到 **8000**。
- 第 3 次：同上。**只要场上还有尸体，这一夜就永远过不完。**

### 这个坑有多常见

40 局 AI 对 AI 实跑（seed 20261101+i，临时埋点统计，已还原）：

| 指标 | 数值 |
|---|---:|
| 报告尸体会议总数 | 319 |
| 其中"开会时夜晚剩余 < 30 秒" | **66（20.7%）** |
| 平均每局触发 | **1.65 次** |

也就是说**每五次会议就有一次**踩在保底上。玩家感知到"时间被重置"完全合理。

## 二、一次会议的完整时间账

### 关键事实：会议期间时钟并没有停

`js/game.js:1505`

```js
if(!G.paused&&!G.over&&!G.meet&&!G.inspect) update(dt);
```

会议期间 `update()` 整段跳过，所以 `G.t` **冻结**在会议开始前的值。
但 `G.phase` 是一个**墙钟相位**（`SKClock.newPhase('night', now, NIGHT*1000)`，
`js/engine/clock.js` 里 `remaining = max(0, endsAt - now)`）——它的 `endsAt` 是绝对时间戳，
`performance.now()` 一直在走，所以**相位在后台照常到期**。

也就是说：会议期间 `G.t`（冻结）和真实相位（在跑）是**两套时间**。
设计上用"会议结束后重建相位"来抹平这个差异，见下。

### 开场：把剩余时间抓下来

`js/game.js:4912`

```js
const remainMs = kind==='night'
  ? (G.simMode ? Math.max(0,G.simT||0)*1000
               : (G.phase ? SKClock.remaining(G.phase,performance.now()) : NIGHT*1000))
  : NIGHT*1000;          // ← day / pre 直接给满 120 秒
```

- `kind==='night'`（**报告尸体＝UI 上的"紧急会议"**）：抓当前相位剩余，正确。
- `kind==='day'`（天亮会议）/ `'pre'`（开局）：直接给 `NIGHT*1000`。
  这两个分支后面根本不走 `nightLeft`，所以是**死值**，但读代码时非常容易误判成"白天会议也占夜晚时间"。

### 散场：算剩余，然后被保底吃掉

`js/game.js:5122-5141`

```js
function finishMeeting(){
  const m=G.meet; ...
  const kind=m&&m.kind;
  let nightLeft=null;
  if(m&&kind==='night'&&m.remainMs!=null){
    nightLeft=Math.max(8000, m.remainMs-(G.simMode?(m.discuss+m.voteT)*1000:
      (performance.now()-(m.startAt||performance.now()))));
  }
  G.meet=null;
  ...
  if(kind==='day') startNight(true);        // 天亮会议 → 直接进下一夜
  else if(kind==='pre') startNight(false);
  else if(nightLeft!=null){                 // 紧急会议 → 回夜晚
    if(G.simMode){G.simT=nightLeft/1000;G.t=G.simT;G.phase=null;}
    else G.phase=SKClock.newPhase('night',performance.now(),nightLeft);
  }
  runInvariants('meetingEnd');
}
```

**三个问题叠在一起：**

1. **`Math.max(8000, …)` 是硬保底**：扣完会议时长后不管剩多少（哪怕是 −22 秒），一律抬回 8000ms。
2. **没有"扣光了就天亮"的分支**：`nightLeft` 永远是正数，`dawn()` 永远不会被会议触发。
3. **保底可以被反复触发**：下一次会议抓到的 `remainMs` 就是这 8000，再扣再抬，形成**不动点**。

数学上就是：`f(x) = max(8000, x − 30000)`，`f(8000) = 8000` —— 8 秒是一个**吸引子**，掉进去就出不来。

## 三、影响面

| # | 影响 | 说明 |
|---|---|---|
| 1 | **夜晚可以无限续** | 只要尸体够多，一夜可以无限拖。任务方永远等不到天亮，异形可以靠"反复报尸体"把节奏锁死在夜里 |
| 2 | **UI 承诺与实现不符** | 会议副标题写着「讨论 25 秒 + 投票 5 秒**（从夜晚时间里扣）**」（`js/game.js:4923`），实际扣不干净 |
| 3 | **蒙特卡洛被污染** | `simGame` 里 `elapsed` 用固定 `(discuss+voteT)*1000`，同样吃这 8 秒保底；约 20% 的会议会让夜晚多出 8 秒，`nights/game`、`knives/game` 等指标都有系统性偏差 |
| 4 | **玩家观感割裂** | 会议里明明看到"剩余 10 秒"，散场后又是 8 秒，再过 8 秒才天亮；如果这时又有人报尸体，玩家会觉得时间根本没动 |

## 四、修复方案（三选一）

### 方案 A（推荐）：去掉保底，扣光就天亮

```js
if(m && kind==='night' && m.remainMs!=null){
  nightLeft = m.remainMs - elapsed;          // 允许 ≤ 0
}
...
if(kind==='day')      startNight(true);
else if(kind==='pre') startNight(false);
else if(nightLeft!=null){
  if(nightLeft<=0) dawn();                   // ← 新增：会议把夜晚耗光 → 直接天亮
  else { ...恢复夜晚... }
}
```

- **完全符合你说的"应该立刻切到第二天白天"**。
- `dawn()` 会 `G.t=0`、清故障、`checkWin()`、然后 `openMeeting('day')`——也就是"第二天白天的全员会议"，链路是现成的。
- 注意顺序：`finishMeeting` 里必须先把 `G.meet=null` 再调 `dawn()`（否则 `openMeeting` 会在会议未清场时开新会）。现在的代码 `G.meet=null` 在分支之前，安全。
- 风险：**深夜报尸体可能"散会即天亮"**，玩家来不及反应。可以给 `dawn` 的 day 会议标题加一句"会议拖到了天亮"。

### 方案 B：保底改成"每夜一次、且更短"

```js
const GRACE = 3000;
if(nightLeft<=0 && !G._nightGrace){ G._nightGrace=true; nightLeft=GRACE; }
```
- 保留"散会不至于立刻天亮"的手感，但**一夜只续一次**，第二次必天亮。
- 代价：多一个 `G._nightGrace` 状态（`startNight` 里清零），规则对玩家不够直观。

### 方案 C：保底保留，但记账到下一夜

把多给的 8 秒从下一夜的 120 秒里扣掉（`G.carryDebt`）。
- 时间总量守恒，但玩家会看到"下一夜莫名短了 8 秒"，更难理解。

**建议走 A**，并在 day 会议的标题/副标题里明确"这一夜被会议拖到了天亮"，把信息给足。

## 五、修完要补的验证

现在门禁里**没有任何一条断言覆盖"会议消耗夜晚时间"**，所以这个 bug 一路绿灯。建议同批加：

1. **单次扣减**：夜晚压到 10 秒 → 开 night 会议 → 模拟 30 秒 → 散会后 `G.t <= 0`（或直接进入 day 会议）。
2. **不许无限续**：连续开 3 次深夜会议，断言 `G.night` 递增、且不会出现"三次都在同一夜"。
3. **正常情况不变**：夜晚剩 90 秒开会 → 散会后剩余 ≈ 90 − 会议时长（±1 秒）。
4. **仿真与真实一致**：`simGame` 里同样的场景，`G.night` 推进次数与真实模式一致。
5. **不变量**：`runInvariants('meetingEnd')` 全过；`G.t` 不出现负值。

## 六、顺带发现的两个小问题（不影响本 bug，可一并处理）

### 6.1 会议事件的 `kind` 被自己的 payload 覆盖

`js/game.js:4902`

```js
logEvent('meeting',{kind:kind, ...});
```

而 `logEvent` 是 `Object.assign({kind:kind,...}, data)` —— `data.kind` **覆盖**了事件类型。
于是事件流里根本找不到 `kind==='meeting'` 的条目，它变成了 `'night'` / `'day'` / `'pre'`。
本次调查一开始就被这一点误导过（按 `kind==='meeting'` 过滤结果为 0）。
建议把 payload 字段改名成 `meetKind`。

### 6.2 `remainMs` 对 day / pre 的取值是死代码

`js/game.js:4912` 的 `: NIGHT*1000` 分支永远不会被 `finishMeeting` 用到（那里只处理 `kind==='night'`），
但它的存在让人误以为"白天会议也占夜晚时间"。建议直接写 `null` 并在注释里说明。

## 七、一句话总结

**不是时间重置，是保底把时间钉死在 8 秒。**
`f(x) = max(8000, x − 会议时长)` 在 `x=8000` 处有不动点，所以深夜每开一次会就原地踏步一次；
修法是把 `max(8000, …)` 换成"允许 ≤ 0，≤ 0 就 `dawn()`"。
