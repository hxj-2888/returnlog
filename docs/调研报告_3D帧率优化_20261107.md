# 调研报告 · 3D 帧率优化（不降画质） — 2026-11-07

> 用户口径：**「性能瓶颈这个可以进行游戏优化，只对玩家可见的地方进行渲染，其他地方静默加载。并且搜索业界的游戏帧率优化方法，先不要采用这种直接压画质的粗暴方法。」**
> 本报告据此撤销上一轮「1024² → 256²」的降采样路线，改为「高分辨率贴图 + 可见性优化 + 共享材质」。

**归纳**：掉帧是三个问题（GPU 算不过来、CPU 批次太多、显存装不下），降压贴图只治显存，且牺牲画质。用户要求的「只对玩家可见处渲染 / 其它静默加载」正对应业界的两层做法：**分区可见性（portal/room streaming）+ 距离剔除 + 贴图按可见性流送**。

## 二、Godot 4.6 / GL Compatibility 下可用项

| 手段 | API / 配置 | 本轮采纳 |
|---|---|---|
| 视锥剔除 | 引擎默认开启 | 已有，无需改 |
| 距离剔除 | `GeometryInstance3D.visibility_range_end` + `visibility_range_end_margin`（迟滞） | ✅ 采纳 |
| 遮挡剔除 | `OccluderInstance3D` 烘焙 + `rendering/occlusion_culling/use_occlusion_culling` + `Camera3D.use_occlusion_culling` | ⏸ 下一步：需实测 GL Compatibility 支持与 CPU 成本 |
| 自动 Mesh LOD | 导入器自动生成，Project Settings → Rendering → Mesh LOD | ⏸ 下一步 |
| 共享材质 | 复用同一 `Material` / `Texture2D` 实例；项目已有 `_material()` 字典缓存范式 | ✅ 采纳 |
| 分区/静默加载 | 按房间容器切 `visible`，节点常驻内存但不提交渲染 | ✅ 采纳 |
| 贴图流送 | 近处用 1024² 共享外饰，远处/不可见仍用 GLB 内嵌低分辨率档 | ✅ 采纳 |
| 合批 | `MultiMeshInstance3D` | ⏸ 下一步：127 件各绑碰撞/交互点位，改动大 |
| VRAM 压缩 / mipmap | 导入器 BC7 / ETC2；`TEXTURE_FILTER_LINEAR_WITH_MIPMAPS_ANISOTROPIC` | 已有 mipmap，压缩格式后续评估 |
| 淡出过渡 | `VISIBILITY_RANGE_FADE_*` | ❌ 不用：GL Compatibility 忽略透明度，改用 `FADE_DISABLED` + margin 硬切换 |
| 帧回调降载 | `set_process(false)` / `set_physics_process(false)` | ✅ 房间隐藏时同步关闭 |

## 三、本项目瓶颈定位（实测）

- 61 件掩体 GLB 各内嵌 8 张 256² JPEG，**480 张图片实例，去重后仅 16 个名字，重复 30 倍**；材质 449 个实例、133 个不同名字。
- 全船 10 舱共 127 件掩体 / 40 件墙饰各是一个节点，玩家一次实际只看 1–2 间房，但**全船几何每帧都参与提交**。
- `gl_compatibility` 后端无自动合批；`HANDOFF.md:511` 明确「127 件各是一个节点」。
- 上一轮把外饰从 1024² 压到 256² 属于「压画质」，本轮撤销；高分辨率的代价改由「只加载一份 + 只在可见处用」承担。

## 四、本轮落地方案

1. **高分辨率外饰**：`gen-sdxl-skins.py` 输出改为原生 **1024²**（源图本就是 1024² SDXL 成品），不再降采样；normal 同步升到 1024²。
2. **共享材质注入**：新增 `res://assets/textures/cover/` 只存一份 1024² 外饰；`map_builder.gd` 按 GLB 材质名的 role 注入共享 `StandardMaterial3D`。GLB 内嵌的 256² 图保留为远处/静默档 —— 这就是「按可见性决定加载到什么精度」。
3. **距离剔除**：所有掩体 / 墙饰 / 设备 `GeometryInstance3D` 设 `visibility_range_end`（约 32 m）+ `end_margin`（4 m 迟滞）。
4. **房间级静默加载**：按玩家所在房间 + 相邻走廊显示几何，其余房间整组 `visible=false` 并关闭 `_process`；**节点与数据不卸载**，进门即时恢复，无加载卡顿。
5. **量测**：新增 `--bench`，落盘 FPS / draw calls / 帧内对象数 / 纹理显存，优化前后可 A/B。

## 四之二、A/B 实测（2026-11-07，非 headless 1280×720）

`--bench-all`（强制全渲染）与 `--bench`（距离剔除 + 房间级静默加载）同一场景、同一机位对比，
读数落盘 `tools/bench-bench-all.json` / `tools/bench-bench.json`：

| 指标 | 全渲染 | 可见性优化后 | 变化 |
|---|---:|---:|---:|
| draw calls | 3109 | **1236** | **−60.2%** |
| 帧内对象 | 3259 | **1386** | **−57.5%** |
| 可见掩体节点 | 127 | **49** | 78 件静默（节点常驻内存） |
| 共享高分辨率材质 | 8 | 8 | 整船只 8 个 Material / 20 张 1024² 图 |
| 纹理显存 | 417 MB | 417 MB | 持平（见下） |

结论：**不降一像素画质，靠剔除把提交量砍掉六成**。FPS 采样受窗口启动与 120 帧采样时长影响
（两次分别 7.2 / 1.0），不作为结论依据；以 draw call、帧内对象、静默节点数为准。

纹理显存未下降的原因：61 个 GLB 仍各内嵌 8 张 256² 图（480 张、去重仅 16 个名字），
被共享材质覆盖后已不参与渲染，但 Godot 导入时仍抽成独立资源常驻显存。
下一步用 `export_materials='PLACEHOLDER'` 重导可把这部分清掉，预计显存显著下降。

## 五、明确不做

- 不再降低贴图分辨率、不再减少材质通道来换帧率。
- 本轮不做 `OccluderInstance3D` 烘焙（GL Compatibility 支持需实测，且 CPU 成本需量测后再决定）。
- 本轮不做 MultiMesh 合批 / 自动 LOD（结构性改动，单独放行）。
- 不改几何、不改碰撞、不改交互点位、不改 2.5D 平衡。

## 六、下一步（需放行）

1. 用 `--bench` 采集「优化前 / 共享材质 / 距离剔除 / 房间剔除」四组读数，确认瓶颈是否从纹理资源数转移到 draw call。
2. 若 draw call 仍高 → `MultiMeshInstance3D` 合批同类掩体（保留碰撞代理）。
3. 实测 GL Compatibility 遮挡剔除；室内飞船场景预期收益大。
4. 贴图导入改 VRAM 压缩格式（BC7 / ETC2），保持 1024² 观感。
